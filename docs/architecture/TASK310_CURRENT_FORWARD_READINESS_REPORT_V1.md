## 2. API and immutable contracts

`CurrentForwardReadinessService(db).build(*, request)` accepts `CurrentForwardReadinessRequest` (`current-forward-readiness-request-v1`) and returns `CurrentForwardReadinessReport` (`current-forward-readiness-report-v1`). New models use strict, frozen, extra-forbid Pydantic configuration. Native upstream objects retain their own versions and semantics.

The request explicitly supplies:

- A deterministic nonempty unique sequence of exact positive Bond IDs; normalized to Bond ID ASC without changing membership.
- `as_of_date`, UTC-aware `evaluation_at` on that UTC date, reviewed 40-character code SHA and exact `moex` context.
- Optional `SourceContext`: collection identity, actual source observation timestamp, exact Bonds/BASE request context, a full Task296C2 frozen admission artifact, expected artifact/source-bonds hashes, optional validated Task296C1 preflight and optional per-UID account evidence.
- Optional reviewed Task303 Genesis plans keyed by a unique member of the frozen seven-capital grid. These are inputs, not generated by this REPORT.

Missing source context is a valid diagnostic situation, not fabricated evidence. If a supplied envelope is malformed, hash-tampered or internally contradictory, validation fails closed before application SELECTs. Existing frozen admission validation/replay and preflight validation are reused. The artifact's historical `core_m3_complete_bond_ids` are not reused as current CORE proof: current Task299/298 results determine coverage.

`AccountEvidence` contains UID, UTC observation time, supplied permitted/unknown/restricted fact, passed test identifiers and an evidence hash. `account_fingerprint()` hashes all fields except its own hash with tests in sorted order. This is an integrity binding, not a digital signature or independent confirmation of a broker statement. No account numbers, tokens or request credentials are needed.

## 3. Time and source authority

Source availability/qualification and supplied account facts have a fixed maximum age of **86,400 seconds** relative to the explicitly supplied `evaluation_at`. Exactly 24 hours is accepted; older or future observations cannot establish current eligibility. Missing observation time stays unknown. Frozen artifact `captured_at` is never substituted for source observation time.

Existing market/curve age 7, liquidity lookback 30 and minimum observation dates 5 remain unchanged. No wall-clock call determines report semantics. Caller input cannot override these v1 thresholds.

`SOURCE_FACT_VERIFIED` means a fact is present in a validated supplied frozen input and exactly bound to the current canonical projection. It does not mean this service contacted MOEX/T-Invest, verified personal legal access or proved an actual fill. UNKNOWN, CONFLICT and UNAVAILABLE remain distinct.

Required tests are per UID. SOURCE_EMPTY does not require account test proof. Missing/unknown tests or nonempty tests not covered by fresh permitted account evidence remain unknown. Explicit restrictions remain restrictions. No qualified-investor status is assumed and qualified-only instruments are excluded from source-eligible execution witnesses.

## 4. Identity and investability scope

### Task310A current tradability authority

Operational safety review baseline: `a1046d8b94a09581c149e48a8ff9d4ea2b142455`; both baseline workflows completed successfully. This revision changes only Task310 diagnostics, guards and credential transport. Native Investment/Risk/Strategy/Shadow/OFZ and historical financial contracts/formulas are unchanged.

The explicit report policy is `FRESH_BROKER_API_POSITIVE_WITH_EXPLICIT_INACTIVE_VETO_V1`. Current source tradability requires **both** exact `api_trade_available=True` and `buy_available=True`, bound to the validated UID and a genuine observation no more than 24 hours old and not in the future. This is reviewed broker-API authority for this diagnostic, not an independent MOEX trading confirmation, personal fill guarantee or documentary claim that an exchange supplied these raw fields.

| Raw activity evidence | Broker facts | Diagnostic and eligibility effect |
|---|---|---|
| Missing/null `is_traded`, no explicit inactive status | Both positive and fresh | `active_status=SOURCE_FACT_UNKNOWN` remains unchanged; independent `tradability_status=SOURCE_FACT_VERIFIED`, basis FRESH_BROKER_API_POSITIVE. Other gates still required |
| Positive raw activity | Broker availability unknown | Activity may be a known raw fact; tradability remains UNKNOWN, never inferred from raw activity alone |

The report version remains v1 with an explicit versioned tradability policy; older reports lacking the new mandatory finding fields must be re-evaluated, not relabeled or granted new authority. New report hashes include these fields/policy. Identical reviewed inputs remain deterministic within this revision. No safety review creates a production-readiness or Day0 grant.

## 5. Read-only snapshot ownership

The service refuses an absent/unprotected transaction. PostgreSQL must already be REPEATABLE READ or SERIALIZABLE and READ ONLY. SQLite must already be query-only with an active physical transaction. `no_autoflush` alone is not sufficient.

Delegation uses a new ORM Session/identity map bound to the caller's same Connection with `join_transaction_mode="rollback_only"` and autoflush disabled. This prevents caller-owned dirty ORM values from changing the observed persisted evidence. The service neither commits nor rolls back the caller's transaction; caller new/dirty/deleted objects remain untouched.

Its own application query is a narrow scalar Bond ID/ISIN/SECID projection for requested IDs. Upstream existing services perform their established read-only queries. No source client, controlled importer, terms bridge APPLY, Genesis PLAN/APPLY, activation service or scheduler is invoked.

## 11. Deterministic hashing and bounds

Reuse the existing canonical iterator: sorted object keys, ASCII escaping, compact separators, exact Decimal strings and ISO dates/timestamps, with nonfinite JSON values rejected. Report SHA excludes only its own SHA. The normalized full request fingerprint includes the genuine observation timestamps, full supplied frozen evidence, code identity and policies. Changes to captured metadata also change the outer report identity even where a legacy native artifact intentionally excludes that metadata from its own SHA.

Legacy StrEnums enter the iterator through JSON-mode Pydantic values. Native Shadow/Genesis linkage uses the original Task303/304 digest and its numeric canonicalization; it is deliberately distinct from a new exact-content request/report fingerprint. Original Python types are validated before JSON serialization so bool-as-int tampering cannot be normalized into valid input.

Paths, database URLs, output destination, current clock and runtime measurements are not hashed or returned. Account and expected native source hashes are checked before DB access. The runner rejects duplicate JSON keys and nonfinite constants, detects input-file drift before publication and never echoes SQL/connection/filesystem exceptions.

Runner input and output limits are 32 MiB each; no silent truncation. Output uses canonical chunks. An explicit output file is staged privately and atomically published without conflicting overwrite; identical reruns are idempotent. Raw source payloads are not republished in report findings. No persistent report is created unless `--output` is supplied.

## 12. Runner and future operator invocation

Only mode `REPORT_CURRENT_FORWARD_READINESS` exists. Explicit `--input`, `--expected-source-sha256` and `--expected-code-sha` are required, plus exactly one of `--database-url-file` (recommended for credentials) or a **passwordless** `--database-url`. Inline URL passwords, secret-bearing query parameters, service/options indirection and endpoint overrides are refused. There is no DATABASE_URL/settings fallback. PostgreSQL requires explicit nonblank host/database/user; absent port is explicitly fixed to 5432 instead of inheriting PGPORT. Query-only host/service configurations without a URL host are unsupported in v1. Passwordless driver-native authentication still requires a reviewed trusted operator environment; the recommended secret-file path supplies explicit credentials for a dedicated read-only role.

The secret file is a single UTF-8 URL line, maximum 16 KiB, with regular-file/no-symlink/reparse checks, descriptor identity checking and bounded reading. On POSIX it must be owned by the effective runner UID with no group/other mode bits (normally 0400 or 0600). On Windows, the operator must provision/review an owner-only DACL; mode bits do **not** validate Windows ACLs. Automated production permission enforcement described here is POSIX/Linux. Do not claim a Windows ACL was checked by this code. Prefer the reviewed rootless Linux operator container when that prerequisite cannot be established.

Provision the file through a secret manager or private editor/secure input mechanism, not a literal-password shell command. Mount it read-only at `/run/secrets/task310-db-url`, readable only by the runner UID, separately from input/output artifacts. The file is never copied to the report, request, semantic fingerprint or log. Credential-file/input/output path overlap is rejected. The runner never prints a URL or raw driver exception; engine echo is disabled and parameters are hidden. Credentials necessarily exist in process memory for connection creation; no memory-zeroization guarantee is made.

The expected source SHA is `fingerprint(request.source_context)` in this contract's canonical representation; native artifact/source-bonds expected hashes are additionally mandatory inside a supplied artifact context. Expected code identity binds the declaration; it is not a measurement of deployed binaries. Pin reviewed checkout/image separately.

The runner owns a PostgreSQL repeatable-read/read-only or SQLite query-only physical transaction and always rolls it back. It never commits. Source requests remain zero; an explicitly configured database connection is the necessary read-only access, not a live MOEX/T-Invest request.

Persistent SQLite URLs additionally require an explicit `file:` URI with `mode=ro&uri=true`; query-only alone cannot prevent file creation at connect time. Embedded URI query/fragment components in the database name are refused. Missing database files therefore fail without being created. Plain `sqlite://` / `:memory:` remain available for isolated fixtures **without query parameters**: a URI suffix could turn the supposed memory name into a disk filename. No fixture creates a shared/production database.
